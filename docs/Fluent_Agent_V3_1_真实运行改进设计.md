# Fluent Agent V3.1：真实运行后的改进设计

日期：2026-09-20。状态：四个代码改造批次已完成；确定性回归已通过，独立真实验收待执行。

本方案基于新 UI 的 NACA0012 实测与当前代码，目标是让用户只需提供工程需求、回答物理澄清并审批，就能完成规划和执行。表达式语法、能力目录、变量命名、单位和编排错误应由系统处理。延续现有 LangGraph、Fluent Runner、Optuna、Case 指纹和独立复算机制。

## 3. Agent 与服务端的职责

Agent 负责理解变量含义、从扫描目录选择能力、提出物理关系、识别代理适用条件、确定缺失物理信息并生成映射。服务端负责公开可用契约、验证并执行已批准的映射，以及提供准确的修复反馈。

可以固化到系统中的内容：

- DSL 的语法、算子、参数数量、单位规则和引用示例。
- ID 冲突检测、目录成员校验、当前 Case 可执行性检查。
- 修复路由、超时/取消、并发控制、审批和版本管理。
- 来流速度、材料、湍流模型等固定条件的读取与运行前核对。

仍然需要用户确认的内容：缺失的坐标系和角度符号、研究范围与工程约束、是否接受有特定适用条件的代理，以及最终实验审批。

软件不会根据变量名字私自补出角度正负号或能力选择。任何改变物理含义的建议都生成新方案版本。未来若引入固定物理模板，须记录 template_id/version，并在自主性报告中与模型原创映射分开统计。

## 4. DSL 与变量契约

新增 `mapping_contract.py`，集中声明每个算子的名称、输入数量、标量/向量类型、输入输出单位规则、有限数约束。Schema、evaluator、validator 和 LLM 上下文均从该定义生成，防止各自维护白名单。

表达式仅允许三种互斥形状：

```json
{"ref": "semantic_variable_id"}
{"value": 0}
{"op": "add", "args": [{"ref": "a"}, {"ref": "b"}]}
```

用互斥子模型/JSON Schema union 表达约束；算子使用 enum，递归节点同样校验。提示中明确 `sin_deg/cos_deg` 接收度制角度，普通 `sin/cos` 不在本版契约内。示例展示通用语法，验收提示不嵌入当前 NACA Case 的完整答案。

优先使用 Provider 确实支持的严格 JSON Schema 输出；不支持时记录 `schema_enforcement=local`，使用同一契约提示、确定性验证与有限修订。不能将 `json_object` 宣称为服务端严格 Schema 约束。接入时验证递归 Schema/union 的兼容性，不默认为所有中转服务都支持。

变量规则：

- `VariableIntent.id`：语义变量身份，版本内稳定，不能复用扫描参数 ID。
- `semantic_key`：来自能力目录的语义类别，不要求等于变量 ID。
- `proxy_variables`：独立的中间变量，不与语义变量、上下文变量、原生参数重名。
- Fluent 参数 ID：由绑定和 MappingSpec 引用，单位由扫描目录给定。
- `source_units/output_units`：必须完整且一致；系统核对，缺失项反馈给生成节点。

增强 validator：递归检查正向与反向表达式的算子和引用；检测环、覆写输入、同名异单位、跨映射冲突、向量分组不完整。采样增加组合边界及固定种子的内部点，避免多变量只检查全最小/全最大/全中点三个组合。采样并非数学证明，因此每个 Trial 的实际映射值仍做边界、有限数与单位向量检查。

固定条件需进入结构化契约，例如 `fixed_conditions`，记录值、单位、来源和验证方式。若用户要求 40 m/s 而扫描值不是 40，必须形成可审批的固定赋值或阻断，不能仅把“保持 40”写进 assumptions。每个 Trial 保存固定条件与方向写入回读证据。

## 5. 节点修复与版本管理

为 Task Parser、Classifier、Mapping Designer、Mapping Reviewer 分别提供职责提示。Parser 只询问缺失工程信息；Classifier 接收允许的 semantic_key 与能力关系；Designer/Reviewer 接收完整 DSL 契约。节点不能因不属于本节点的字段而向用户索要 Schema。

错误改为结构化问题：

```json
{
  "code": "EXPRESSION_FORM_CONFLICT",
  "node": "mapping_designer",
  "path": "mappings[0].forward_expression.proxy_angle",
  "severity": "blocking",
  "expected": "exactly one expression form: ref, value, or op",
  "repairable": true,
  "status": "open"
}
```

引用形式错误返回 Reviewer；变量 ID 冲突返回 Parser；能力不兼容返回 Classifier；缺少物理信息才进入用户澄清。错误涉及上游时，必须失效并重建其下游产物。

状态至少包含 `plan_revision`、`planning_attempt_id`、`current_node`、本轮修订计数、`active_issues`、`issue_history`。同一修订链最多 3 次自动修复；用户变更需求或显式重试开启新 attempt，本轮计数归零，历史总数保留。自动节点不能自行开启新 attempt 无限规避上限。

验证通过时，已修复问题进入 history，active_issues 清空。旧错误不能继续成为红色阻断。界面的“可审批”由确定性状态决定，不能直接相信模型回复中的“已生成可审批方案”。

保留首轮原文 `original_request`，另存当前意图与修订差异。普通“继续”保持当前意图；明确修改目标、预算或范围则更新当前意图，并失效旧审批。

## 6. 规划运行、超时与取消

将长连接式 `POST /api/agent/messages` 改为提交后台规划任务，返回 HTTP 202 与 attempt_id。前端继续使用状态轮询；首版无需新增 SSE。前后端同时升级该响应契约，旧调用方使用独立兼容适配，避免同一路由在不同模式下含糊返回。

建议新增：

- `GET /api/agent/attempts/{id}`：阶段、排队/调用/校验/修复状态、耗时、终态。
- `POST /api/agent/attempts/{id}/cancel`：幂等取消当前规划。
- `POST /api/agent/attempts/{id}/retry`：保留历史、创建新 attempt。

建议首版默认值（需要实测调优，不是性能承诺）：单次模型调用 120 秒、一次完整规划 attempt 总预算 480 秒、网络瞬态错误最多重试 1 次，退避和排队消耗同一总预算。自动语义修复与网络重试分别计数，SDK、runtime、graph 不得各自叠加独立重试额度。

默认规划 reasoning 可设为 medium，通过 Fluent 专用配置与每次调用参数覆盖；不临时改写全局 model_catalog。高级设置允许用户选择更高强度及相应预算，记录 effective_reasoning。不得静默更换模型、Provider 或推理强度。

取消分两个层面：本地立即使 attempt 失效、禁止迟到结果写回，并尝试取消底层请求；若上游无法确认取消，显示“本地已取消，上游状态未知”。浏览器 AbortController 只控制前端等待，不能替代服务端取消。

显式处理 TimeoutError、CancelledError、解析失败、Provider 错误和进程重启中断，持久化 `timed_out/cancelled/failed/interrupted`。watchdog 按持久化 deadline 将无进展的活动 attempt 收敛为终态；它不能生成“仍在推理”的虚假心跳。

同任务只允许一个活动规划 attempt。消息、Case 切换、审批、运行和新任务操作共享短临界区与版本比较，长模型调用期间不持有全局锁。提交新需求时显式取消旧 attempt 或返回冲突；写 checkpoint 前核对 task/model/case/revision/attempt 全部身份。不同任务不应被全局锁串行阻塞。

审计异步取消路径，特别是当前 runtime 的 `asyncio.to_thread(slot.acquire)`：取消等待后后台线程仍可能取得 slot，需要确保许可不会泄漏。以并发取消压力测试验证，不能只给最外层再套 timeout。

## 7. 审批与执行模式隔离

新增服务端持久字段 `planning_mode=agent_v3|manual`。进入 Agent 流程时即设为 agent_v3，不能等到 resolved_task 生成才认定模式。

V3 审批必须同时满足：当前 attempt 已结束于 awaiting_approval、ResolvedTask 可执行、active_issues 无阻断、Case 身份一致、没有运行任务，且审批请求携带当前 revision 与 resolved fingerprint。

V3 启动只接受批准的 revision/fingerprint 和幂等键，由服务端读取冻结对象编译；不再让旧手动表单重复提交参数列表、预算与迭代数。重复点击不创建第二个 Campaign。100/1000 的预算差异统一为共享硬上限和可配置实际限额，前端从后端读取。

V3 未完成、失败、超时或被取消时，审批与启动均返回明确错误，不允许回退 manual。手动模式通过显式入口新建任务，单独标识和记录；不共享 V3 的旧审批。

规划输入和审批指纹还需包含固定条件、DSL/Registry 版本及有效模型配置快照。结果解释请求失败只影响“结果解读”，不能将已成功的 Fluent 求解改判为失败。

## 8. 新 UI 的简约交互

保留“定义任务 → 审查方案 → 运行监控 → 结果交付”四步结构。页面默认呈现工程信息，参数 ID、JSON 和异常栈放入可展开的技术详情。

| 状态 | 主内容 | 主操作 | 运行权限 |
|---|---|---|---|
| 未提交 | Case、维度、研究目标 | 生成方案 | 禁止 |
| 正在规划 | 当前阶段、已用时间、真实调用/修复进度 | 取消规划 | 禁止 |
| 需要物理澄清 | 简短问题及已知条件 | 补充并继续 | 禁止 |
| 系统正在修复 | 问题摘要、修复次数 | 取消规划 | 禁止 |
| 修复失败/超时 | 失败阶段、可操作建议 | 重试；技术详情 | 禁止 |
| 等待审批 | 变量、目标、固定条件、代理假设、预算 | 批准并运行 | 满足服务端门禁时允许 |
| 执行/复算 | Trial 进度、Gate、复算阶段 | 查看实时结果 | 不允许重复启动 |
| 完成 | 样本最佳点、复算结论、结果适用边界 | 查看/导出产物 | 新实验需独立操作 |

V3 全程隐藏 legacy editor；状态不完整时显示草稿，而不是旧版手动参数。模型维度初始化从 spec/profile 读取，避免二维 Case 初始选成 3D。当前预算、底部计数、运行表格使用同一服务端来源，未执行时明确“预算 3，已完成 0”。

审查卡片默认显示“攻角 4–8° → 入口方向；固定速度 40 m/s；固定几何代理”。展开后显示公式、单位和坐标约定，继续展开才显示 ID/DSL。存在 MAPPED_PROXY 但映射未验证时显示“映射待完成”，仅全部 DIRECT 且绑定通过时显示“无需代理映射”。

修复记录折叠显示“已自动修复 N 项”；当前阻断单独显示。补全 reviewing_mapping、failed、timed_out、cancelled 等中文状态。连接失败显示最后更新时间和“数据未更新”，不能继续显示新鲜的健康状态。

结果页将“计算完成”“独立复算通过”“几何验证未进行”分开显示。Cl/Cd 26.308 应称为“本轮样本最佳值”，三次采样不能称为全局最优。独立复算相同也不等于数值不确定度为零。

## 9. 证据与自主性统计

每个 attempt 记录：模型/Provider、实际 reasoning、节点、请求与响应时间、可用时的 Provider request ID 和 token usage、超时/取消/重试、输入契约哈希、验证结果。Provider 不返回 usage 时保留 null，不能填 0 或据此宣称未调用。密钥和认证头不入日志；必要的响应正文仅保存在本地审计产物中。

每条人工输入记录来源与类别：初始需求、物理澄清、审批、技术修复、手工对象编辑。分类由实际操作者/测试协议和产物差异支持，不能仅凭 Agent 自评。测试报告包含：

- 是否真实模型调用及其证据；是否真实 Fluent 执行及 Trial/stdout/回读证据。
- 模型节点调用数、自动修复次数、规划耗时与求解耗时。
- 人工物理澄清数、人工技术提示数、手工契约修改数。
- 结果是 direct 还是 proxy，数值复算与几何验证分别达到什么状态。

自主规划验收要求后两类技术干预计数均为 0；工程审批和必要物理澄清不计为技术代做。

具体完成项：

- `planning_mode=agent_v3|manual` 持久化；审批和启动按模式强制隔离，V3 非待审批状态不能借用 legacy plan。
- 版本化 `mapping_contract.py`；表达式算子 enum、参数数量、正反向递归、循环引用、跨映射及命名空间碰撞检查，并把同一契约传入 Designer/Reviewer。
- 固定物理条件进入 `SimulationTaskObject.fixed_conditions`，在编译、原生参数基线和 Trial 结果中保留核验证据；扫描值不一致且未声明运行回读时会阻断。
- `original_request`、`current_intent`、`plan_revision` 与 `planning_attempt_id` 分离；物理澄清不重写研究目标，明确方案修改才产生新 revision。
- 后台 attempt 记录持久化；同任务禁止并发规划；取消、超时、失败、重启中断均形成终态；重试创建新 attempt，不覆盖旧记录。
- 每个模型节点写 JSONL 调用审计，记录模型、运行时、实际 reasoning、契约哈希、耗时、结果和网络重试；Provider 未给出的 request ID/token usage 保留 `null`。
- UI 在进入 V3 时立即隔离手动编辑器，显示后台阶段、耗时、取消/重试、当前/历史问题、固定条件与结果适用边界；二维默认值和预算统一读取服务端。
- V3 启动由冻结对象编译并要求幂等键；重复请求返回同一 Campaign，不创建第二次运行。

尚未自动宣称完成的是第 11 节的真实验收：需要重新建立干净任务，在不给公式、参数 ID、操作符或 JSON 技术提示的条件下完成三次独立规划，并任选一次执行真实 Fluent Trial 与复算。该验收是产品能力证据，不再属于代码改造批次。

## 11. 验收标准

确定性回归：

1. 注入普通 sin/cos、op+ref、op+value、反向未知算子、变量碰撞、单位缺失、缺 XYZ、循环引用及不支持能力，均能准确拒绝并返回所属节点；三次修复失败必须终止。
2. 新版本重置局部计数，历史次数保留；技术修复不重写研究目标，明确需求修改更新当前目标并使旧审批失效。
3. 在每一种 V3 非可审批状态直接请求审批/启动，均被服务端拒绝，即使存在合法 legacy plan；双击与重复 HTTP 请求至多创建一个 Campaign。
4. 模拟超时、限流、断网、取消、重启、双并发请求和迟到响应：状态必达终态、无旧结果覆盖、无许可泄漏、无意外启动 Fluent。取消后下一次状态刷新可见；健康进程下以 2 秒为本地取消状态反馈目标。
5. 二维 Case 默认显示 2D，待澄清时无手动编辑器/可用启动按钮，修复成功后无历史红色阻断，页头/侧栏/底栏预算一致，刷新能恢复状态。
6. 固定速度与扫描/运行值不一致时不能通过；求解成功而解释失败时结果仍显示已完成并保留验证产物。

真实验收分开记录规划能力与求解能力：

- 新建干净任务，使用本次原始 NACA 自然语言目标；操作者不提供公式、ID、操作符或 JSON 示例，仅回答物理澄清及进行最终审批。
- 连续 3 次独立规划均通过契约验证，人工技术提示和手工契约修改均为 0，且自动修复不超过配置上限；这是首轮发布门槛，不代表统计稳定性已被充分证明。
- 增加坐标符号改变、多个入口、缺少单位和不支持几何能力的规划样例；缺信息必须追问，不支持必须阻断，防止仅记住 NACA 答案。
- 从无技术提示的成功规划中选一次，经新 UI 审批完成 3 个真实 Fluent Trial 和最佳点复算；按声明的残差/守恒 Gate 判断。采样点无需与旧试验完全相同，不将单个目标数值作为唯一验收标准。
- 再做一个无需代理的直接变量小预算真实闭环，证明 V3 模式隔离后 DIRECT 路径仍能执行。
- 报告同步列出规划成功率、耗时分布、外部模型失败和科学不可行结果；不能删掉失败重试，只保留成功结果。

完成以上验收后，才能将产品表述从“有人协助跑通的 Agent 原型”升级为“在已验收能力范围内可自主规划、经人工审批执行的 Fluent 实验工作台”。
